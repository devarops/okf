Acceptance Test Driven Development (ATDD) is a pattern in Continuous Delivery.
Acceptance tests are written before code as an Executable Specification.
The pattern follows a four-layer separation of concerns.
Test cases are written in the language of the problem domain from an external user perspective.
The Domain Specific Language is shared between test cases.
Protocol Drivers translate DSL commands into interactions with the System Under Test (SUT).
Each SUT communication channel needs its own Protocol Driver.
The SUT is deployed in production-like environments using infrastructure-as-code.
Effective acceptance tests evaluate the system through public interfaces in life-like scenarios.
They focus on what the system does not how using domain language instead of UI terms.
Humans write the acceptance tests as the primary way to guide AI development.
Well-written acceptance tests serve as precise prompts for AI-generated code.
They also verify that AI-generated code meets the specification.
Grow the DSL pragmatically starting with two or three simple test cases.
Invent the language for a test at the time of writing.
Developers own the tests and the plumbing including the DSL and Protocol Drivers.
The combination with fine-grained TDD can reduce defects by two orders of magnitude.
